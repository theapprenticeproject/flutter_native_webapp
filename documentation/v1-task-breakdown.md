# v1 task breakdown (draft)

**Date:** 2026-11-02. Updated 2026-11-04.
**Purpose:** a list of the changes needed for the v1 test release, with a rough effort for each. We will use it to plan and to track the work.
**Source:** `v1-requirements.md` (it always wins), `tapapp-changes.md`, `backend-plan-feedback.md` and `build-bootstrap.md`.

## How to read this

- **Effort is in working days for one developer who knows the code.** Each task has a low and a high number. They are rough.
- **Two efforts for each task:** **Build** (write the code) and **Tests** (write the automated tests for it). A task is **done only when its tests pass on a developer's machine, with one command (E4).** There is no CI yet. The "Automated tests" column says what the tests check.
- **What stays manual:** the WhatsApp in-app browser, the phone camera and video playback cannot be automated. They are tested by hand on real phones (E2) with a written checklist.
- **Priority.** **P1**: needed for the mid-November test release. **P2**: in the requirements for v1, but it can follow the first test, or we ask if the test group needs it (see A16). **Later**: not in the test release. Other later items (events, a stronger login, tiered rewards and so on) are not listed. See section 2 of the requirements.
- **Depends on** lists the tasks that must be done (or at least started) first. A to E are the groups below.
- **Assumptions:** the test runs on the dev server, not on production. `journey_2026` is the deployed branch (confirmed). The test group is 30 to 100 pre-registered kids. The flow is hardcoded: greeting, video, submission, quiz. Each kid gets a magic link. The three daily feedback windows stay as they are.
- **Dates.** The test release is in mid-November. This list was updated on 3 November, so about 9 to 13 working days remain.

## How to cut (if the team is small)

The smallest slice that is a real test: login, then one activity from Home through Watch, Make, Quiz and Results, with points. That is **B0 to B8, B10, B18, C1 to C6, C9, C10, D0 to D8, D11 (or bundled content), D12, D14, D15, D17, D18, E1 to E5**. Add **B14, C7 and D13** (the feedback link) if the product team approves O-28 in time. If time is short:
1. **Do B0 first.** It decides where the quiz and assignment content lives, and B5, B11, B18 and D4 wait for it. It is the biggest risk.
2. **Bundle the content in the app for the first test** (skip B11 and D11, about 5 to 8 days with tests. Still do B18, because the audio status, the example works and the quiz answer key are needed either way). R-18 says download from the CDN, so this needs your agreement. Switch to the CDN in the next release.
3. **Skip "My projects" and the tags on the Me page** (parts of B8 and D8, about 2 to 3.5 days with tests). Keep points and level.
4. **Skip the picture badge** (D16, about 1.5 to 2 days with tests). It is a nice touch and not needed to run the activity.
5. **Defer the feedback link** (B14, C7, D13 and the Glific work in A10, about 4 to 7 days with tests) if the product team's approval is late. Kids then see their feedback when they open the app, and no WhatsApp message with a link is sent.
6. **Leave P2 out:** the Gallery (B12, D9), Ask TAP (D10), and the small load test (E6). Together this saves about 8 to 12.25 days. Saving every interaction (C9, C10, D18) is P1 since 2026-11-04. If we must cut it, the first thing to cut is the queue consumer (C10): the events wait in the queue and can be written to BigQuery later (check how long the queue keeps them). First ask which of them the test group needs (A16).
7. **Do not cut the tests of B2, B5, B7 and C2.** These tests protect each child's private data, make sure the server checks every answer again, and make sure the points are right.
8. **Run E2 (real phones) in parallel** with the build, starting with the video camera and with what happens when the camera is refused. Bugs found late there cost the most.

## Risks that can add days

- **The quiz and assignment content** (B0, B5, B11) may not be in Frappe. The lead's flow reads it from a Google Sheet, and `submit_artwork` fails when the assignment id is not in Frappe. If the content is not in Frappe, B5 and B11 change. This is the biggest risk.
- **Reading the private Google Cloud bucket from the Worker** (C5) is not tested. If it fails, B6 and the Gallery copy need another plan.
- **Video size** (50 to 100 MB at 30 to 90 seconds): upload on weak connections may need compression in the browser, which may not be possible in the WhatsApp browser.
- **Approvals** (A2) are done, except making `submit_artwork` refuse calls with no key. That one is not approved yet. It does not block the test, and it blocks the key rule for production.
- **The feedback link message** (O-28, approved) needs the Glific team to build the new flow (A10). Without it, the kids get no WhatsApp message with a link to their feedback. They see the feedback only when they open the app.
- **The test kids need Glific contacts with `student_id`** (B10, A11). Without a contact the feedback job skips the kid and does not retry. Without separate `Student` records for siblings, the name picker shows one child.
- **The Figma fixes** (A4) change some frames (the waiting label, the "I watched it" button, the countdown). Building before the fixes can mean small rework in D3 to D7 and in their tests.
- **`tapapp` has few tests and uses raw SQL,** so tasks B1 to B3 may take the high end of their range.
- **A local Frappe test site** (E4, E5) may take longer than planned. The backend tests depend on it. Without CI, someone has to run the tests before each release, so the local command must be fast and simple.
- **The dev server may use the real Glific account** (A18). Then the feedback job could message real children. Check this before the first test submission.
